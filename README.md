## Быстрый запуск в Docker на Windows

1. Установите и запустите Docker Desktop.
2. Дважды щёлкните `start.bat`.
3. Дождитесь открытия страницы [http://127.0.0.1:8000](http://127.0.0.1:8000).
4. Чтобы остановить контейнер, запустите `stop.bat`.

Приложение при старте читает локальные файлы из `data/`, собирает сводку и HTML-дашборд, затем запускает локальный веб-сервер. CSV подключаются как read-only volume и не упаковываются в Docker image. Журнал приложения сохраняется в `logs/application.log`; Docker также показывает сообщения в окне запуска. Сгенерированные `out/`, `logs/` и HTML-отчёт исключены из Git.

## GitHub

Код опубликован в [5postyan/-4](https://github.com/5postyan/-4). Репозиторий публичный. В него отправлены только исходный код, правила, Docker-файлы и документация. Папки `data/`, `out/`, `logs/` и сгенерированный дашборд исключены из Git.

Чтобы использовать GitHub-версию с демонстрационными данными, клонируйте репозиторий и скопируйте в его корень папку `data/` из этого ZIP-архива. Данные останутся локальными и не попадут в Git. Затем запустите `start.bat`.
## Логи

В `logs/application.log` записываются запуск, этапы перехода, проверки приёмки и HTTP-запросы. Ротация происходит при достижении 5 МБ, сохраняются три предыдущих файла. Содержимое исходных строк CSV и секреты в лог не записываются. Подробный журнал кейса по-прежнему сохраняется отдельно в JSONL-файле внутри `out/`.

# Кейс 4 · Запуск энергетического объекта — прототип

Детерминированный конечный автомат из 4 этапов + конфигурируемые проверки + журнал + протокол запуска + карточка запуска (HTML). LLM не используется и статусы не назначает.

## Запуск в чистой среде (Python 3.10+, без сети)
```
pip install -r requirements.txt
python run_demo.py          # 6 объектов + сквозной запуск Building 2 + 11 сценариев → out/
python build_dashboard.py   # → dashboard.html (один файл, открыть в браузере)
```
Результат: `out/results.json`, `out/scenarios.json`, `out/journal_building_2.jsonl`, `out/protocol_building_2.md|json`. Прогон детерминирован (seed 42, демо-часы), все 6 объектов проверяются < 1 с (лимит 60 с).

## Состав
| Файл | Назначение |
|---|---|
| `rules.json` | версия правил **1.0.0** и все пороги (99 %, 30 мин, окно 48 ч, допуски, окно истории, CA-фактор) — не в коде |
| `launch/checks.py` | проверки этапов 1–4, имитатор управления, шаблон дашборда |
| `launch/machine.py` | автомат статусов, правила переходов, журнал, устаревание подтверждений, протокол |
| `run_demo.py` | демо-сценарий и 11 тестовых сценариев ТЗ |
| `data/BuildingN/` | входные файлы (`object.json`, `invoice.csv`, `telemetry.csv`); `data/mapping.json` — откуда взяты |

## Схема потока и правила переходов
```
[1 История] → [2 Реальное время] → [3 Управление] → [4 Дашборды + приёмка] → ГОТОВ
статусы: Не начат · В работе · Заблокирован · Завершён
```
- Этап завершается только если все обязательные проверки `pass/na`. `fail` и `unavailable` блокируют (отсутствие данных ≠ успех).
- Запрос завершить этап при незавершённом предыдущем отклоняется с перечнем зависимостей, материалы сохраняются. Этапы 3–4 не запускают проверки, пока предыдущие не завершены.
- Хэш входов каждого этапа (данные + паспорт + правила + конфиг) сохраняется; при изменении подтверждения этого и последующих этапов становятся неактуальными (`confirmation_stale`) до перепроверки.
- Готовность объявляется только после 4 этапов и приёмки дашбордов (`launch_ready`).
- Текст внутри данных (паспорт, названия блоков) — только данные (сценарий 10).

## Проверки
- **Этап 1:** EAN (18 цифр, различаются) · метки (дубли, шаг 15 мин, UTC) · покрытие 24 мес. с интервалами пропусков · полнота validated/raw · знаки (энергия ≥ 0, CA выдачи ≤ 0) · единицы и выбросы (E = P/4, лимит CA/4) · уникальность истории среди объектов.
- **Этап 2:** сигналы по паспорту (актив + конкретные колонки) · метки/зона · актуальность ≤ 30 мин · полнота ≥ 99 % за 48 ч · правдоподобие (PV ≥ 0, SoC 0–100 %, заглушки 9999, E≈P/4 по знакам) · согласованность с учётом (корреляция, сдвиг зоны, чужой объект).
- **Этап 3:** исторический отклик sent → received → power · тест контура на **имитаторе** (команда, приём, отклик). Реальные команды не отправляются; «отправлено» без приёма/отклика — блокировка.
- **Этап 4:** паспорт (адрес, координаты) · 4 обязательных блока · привязка блоков к объекту · права (оператор — read, без публичного доступа) · приёмка ответственным.

## Метрики (раздел 6), что измерено
- Сценарии ТЗ: **11 / 11** дают ожидаемое поведение (самопроверка по правилам; эталон организаторов недоступен и не использовался).
- Ложно завершённые этапы: **0**. Готовность до 4 этапов: **0** объектов.
- Подтверждения (источник, результат, время, версия правила, хэш входов): **100 %** (23 из 23 обязательных проверок в завершённых этапах).
- Сокращение времени ΔT: **не измерено** — нужен ручной baseline инженера на тех же 6 сценариях. Время машинной проверки: < 1 с на состояние.

## Допущения (уточнить у кейсодержателей)
1. Файлы пришли без привязки к объектам; сопоставление по составу колонок и корреляции (`data/mapping.json`). Для Building 1 и 4 история почти идентична, назначение неоднозначно, обе блокируются проверкой S1.08.
2. Окно 24 мес. = 05.11.2024 … 31.10.2026: строки с 01.11.2026 в выгрузках пусты. Если окно считать до 05.11.2026, Building 5 блокируется по 5 суткам.
3. Точка проверки `2026-11-05T09:15Z` (в последних 4 интервалах `Demand.*` пусто у всех объектов; при точке 10:15Z этап 2 везде блокируется).
4. Пропуск validated закрывается значением raw (правило `fallback_validated_to_raw`, отключается в `rules.json`).
5. Коррекция знака `Grid.power_kW` для Building 2 — демонстрационное «согласованное правило»: оригинал не меняется, коррекция журналируется и меняет хэш входов. На практике исправлять нужно в адаптере (`Multiplier.power`).
6. Дашборды: конфигурация генерируется шаблоном; приёмка в демо — симуляция ответственного.
7. `Configuration_file.json` из набора не парсится (висящие запятые, незакрытые кавычки); заполнение конфигурации не реализовано.

## Ограничения и предложение пилота
**Ограничения:** управление только в имитаторе; пороги демонстрационные; нет UI-загрузки файлов и ролевой авторизации (права проверяются как конфигурация); нет очереди задач и напоминаний; приёмка не аутентифицируется; E≈P/4 даёт ~6 % естественных расхождений.
**Пилот (по паспорту кейса):** один обезличенный завершённый запуск + один объект «в процессе»; доступ только на чтение и тестовый интерфейс управления. Цель: подтвердить правила переходов и пороги, измерить baseline (ручной чек-лист) и ΔT ≥ 30 % на 6 сценариях, заменить имитатор на тестовый контур, подключить загрузку данных и аутентификацию приёмки.
